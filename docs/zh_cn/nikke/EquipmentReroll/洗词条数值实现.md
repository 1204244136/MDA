# 洗词条数值实现

本文面向维护者，说明数值重洗的配置接线、Pipeline／Go 分工及执行约束。使用方式见[任务说明](README.md)，成本估值和候选接受规则统一维护在[概率与期望计算](洗词条概率与期望计算.md#数值重洗成本估值与候选取舍)。

## 配置与职责

任务通过 `operation` 区分效果／数值，通过 `mode` 区分角色／单件。两者相互独立，共用 `EquipmentRerollMain` 入口。

数值模式的角色和单件分别使用总 T 与单件 T 输入选项，最终写入 `EquipmentRerollLockNeed.attach` 的 `operation`、`mode`、`part`、`value_tier_<效果名>`。配置解析与目标校验由 Go 完成。

固定界面差异放在 `assets/tasks/EquipmentReroll.json` 的 `EquipmentRerollOperation` → `Value` case → `pipeline_override` 中，由客户端在启动任务前应用，两种范围共用。调试时直接运行节点，也需要应用该选项覆盖，不能只设置 `attach.operation`。

基本识别与点击由 Pipeline 声明；Go 复用识别节点，处理快照、数值解释、规划及跨节点决策，不保存 ROI、模板或颜色参数。

| 位置                                                      | 职责                                     |
| --------------------------------------------------------- | ---------------------------------------- |
| `assets/tasks/EquipmentReroll.json`                       | 用户选项、数值模式固定覆盖               |
| `assets/resource/pipeline/EquipmentReroll/`               | 页面与锁状态识别、点击、等待及失败路由   |
| `value.go`                                                | 快照校验、范围聚合、可达性与候选解释     |
| `value_cost.go`、`value_plan.go`、`reroll_probability.go` | 成本估值、完整锁方案及概率计算           |
| `value_execution.go`                                      | 冻结计划、跨帧锁证据、核验后提交         |
| `value_action.go`                                         | 配置检查、角色／单件共用选装决策         |
| 扫描、费用和 `pending_result` 组件                        | 识别结果聚合、实际费用记账及候选原子提交 |

Go 文件位于 `agent/go-service/equipmentreroll/`。锁状态读取 `readConfirmLocks` 同时供历史锁恢复和数值锁核验复用。

## 执行与提交

1. 校验配置，扫描所选范围，检查数值与目标可达性。
2. 聚合快照并选择装备，进入数值确认页。
3. 取得稳定的初始锁证据，同步锁状态并冻结本轮完整方案。
4. 先解除多余锁，再按计划顺序新增固定锁、单次锁；每步核验后才更新快照。
5. 读取实际费用并检查预算，执行重洗；结果页出现后才提交费用。
6. 解释候选并决定维持或接受；接受完成哨兵确认返回后，才提交候选数值并重新规划。

效果种类及空槽布局在数值重洗中不得变化；受保护槽的档位不得变化。识别不完整时不得提交候选。单次锁在结果产生后过期，与是否接受无关；结果页重试仍使用本轮实际受保护的源快照。

历史一键加载只在本任务最近实际使用的锁与当前完整计划一致、库存已知且可支付时参与路由。加载后必须验证实际锁位，不能仅凭按钮点击成功就更新快照。

## 识别与失败处理

### 初始扫描

先使用严格的独立数值 OCR；未取得档位时，复用 Pipeline 复核节点修正已知的百分号误读，再按档位表及容差校验。原始 OCR 候选保留在 `value_candidates`，未通过过滤的文本不能直接成为数值。

数值模式中，有效效果缺少可确认档位、或空槽未获确认时，当前槽返回未命中。Pipeline 有界重试，超时显式失败，不提交不完整快照。效果模式不增加这项数值完整性门槛。

### 锁状态与页面确认

锁图标存在明暗变化：彩色未命中不等于未锁。必须有明确的无锁图标或空槽证据；证据不足时返回未知。具体颜色、像素数量及 ROI 以 Pipeline 配置为准。

新一轮初始锁同步要求至少两次明确且一致的完整识别，间隔至少 200ms；未知帧、状态改变或观察过期会重置证据。方案冻结后禁止重新同步初始锁来掩盖操作失败。

刚消费稳定证据、且冻结计划不改变任何锁时，可以直接进入费用识别，省去重复就绪检查。已有方案、加锁、解锁及历史恢复仍须独立核验。

解锁确认组合识别标题、说明及确认按钮；确认后必须验证锁状态与预期一致。上锁同样在核验后提交，不采用乐观写快照。

### 超时与费用

Pipeline 的 `timeout` 限制当前节点等待 `next` 的时间。等待初始锁和就绪识别时，需要给父节点设置有界超时及失败出口，不能只给被等待节点设置超时。初始锁识别节点还必须显式接入规划动作，避免识别成功后执行默认 `DoNothing`。

实际费用必须与冻结方案的首轮模组／密钥总量一致，并检查已知库存；不一致时停止。未知库存可能用于乐观选装，但进入锁定页后若发现计划无法支付，应停止，不能临时换材料。首轮可支付不代表足以完成全部目标。

诊断日志保留规划耗时、期望／实际锁状态，以及当前／候选的剩余成本估值，便于区分识别等待、计算与业务拒绝。

正式回归测试覆盖目标上限、不可达目标、已有锁处理、材料预算、候选取舍、一次性锁过期、费用与状态提交。成本 DP、数值候选枚举和效果首次到达公式均有独立计算交叉验证。

离线回放覆盖确认页、结果页、锁的亮／暗相位及解锁弹窗。截图和一次性 OCR 探针属于本地调试材料，已被 Git 忽略，仓库不附带这些夹具；干净检出不会自动获得它们。保留的可选回放测试通过 `MDA_MAA_LIB` 和 `MDA_RELOAD_SCREENSHOT` 指定框架与截图，通过 `MDA_VALUE_SAMPLE` 选择场景，未配置时跳过。执行回放前应确认样本符合对应断言。

对截图施加 OCR 替换注入，只能验证纠正规则和错误分支，不能代替真实故障画面或完整实机流程。资源加载成功也不等同于 Custom 接线正确或端到端验收通过。
