# 收藏品保养说明

角色预热里的收藏品分支：从收藏品页开始，把当前装备的收藏品一路保养到满级（15 阶段）。可以从两个位置进入：角色详情页（点左上角收藏品加号），或**直接停在收藏品页**——已经装着收藏品时按页面按钮分派：有「保养」就继续保养，有「更换」就执行更换（**R 级 15 阶段可以直接从这里开始**），两个都没有就收尾（SR 满级或已进化成珍藏品）。R 级养满后自动「更换」成 SR 级继续养，SR 级满级即结束。

使用入口见任务卡「角色预热 → 收藏品预热」，运行时代码位于 `agent/go-service/collectible/`，识别与操作节点位于 `assets/resource/pipeline/CharacterPrep/CharacterPrepCollectible.json`。

## 机制

收藏品有两套稀有度（R / SR）与三档保养工具箱（初级 / 中级 / 高级）。每次保养消耗 **10 个**工具箱，加固定经验：

| 档位           | 消耗 | 加经验 |
| -------------- | ---- | ------ |
| 初级（R 箱）   | 10   | +200   |
| 中级（SR 箱）  | 10   | +500   |
| 高级（SSR 箱） | 10   | +1000  |

- 每阶段经验上限：**R 级 1000、SR 级 3000**；条满一阶 → 阶段 +1、经验清零。
- **非常成功**：只与「收藏品等级 + 当前阶段 + 使用的档位」有关，与当前经验无关。命中后**直接跳到下一个 5 的倍数**（0–4 → 5，5–9 → 10，10–14 → 15），不会一次跨两个区间。
- 游戏内提示（点击保养时可能弹出的通知）：

    > 在 5、10、15 阶的区间内，无法保留超出的经验值。
    > 即使非常成功，也无法一次提升超出 5、10、15 阶的区间。

    即跨区间时溢出的经验会被丢弃，这也是分区间统计概率的原因。

## 操作流程

```text
收藏品页（左上角「收藏品」）
  └ 保养（未满级）／更换（R 级满级）
       └ 三档工具箱面板
            ├ 概率采集（缺哪档补哪档，见下节）
            └ 决策 → 选中某一档
                 └ 面板「保养」→ 保养对话框
                      ├ 勾选「跳过保养动画」（已勾选则不动）
                      ├ 设置重复次数（等于上限时直接点 MAX）
                      └ 点「保养」（面板会先闪一下，此时材质还没扣）
                           ├ 每日首次：弹「请摩擦画面来保养收藏品。」小游戏，反复折返摩擦到进度满
                           └ 其余：保养动画（黑屏数秒）
                                └ 结算页「点击任意处进行下一步」
                                     └ 通知「收藏品保养完成」→ 确认
                                          ├ 未满级：回三档面板，继续下一轮
                                          └ 满级：面板关闭回收藏品页
```

部分角色的收藏品升到 SR 15 阶段后可以进化成「珍藏品」。这类角色的收藏品页会多一行说明（「装备并妥善保养收藏品，」+「能将收藏品升级为珍藏品。」，普通收藏品则是「可装备并保养收藏品。」），右下角还多一个「珍藏品资讯」按钮。识别用两者共同的片段「保养收藏品」匹配，两种文案都能进流程。**珍藏品自身的升级逻辑不在本任务范围内**，进化后不会去点任何按钮。

R 级养满 15 阶段后，页面按钮变成「更换」：更换页确认 → 通知确认 → 「替换完毕」→ 点击任意处，收藏品换成 **SR 5 阶段**，随后继续保养。

**只有 R 级 15 阶段（满级）才有「更换」**，其它等级页面只有「保养」，所以不存在「按经验换算」这条曲线，只是一个固定跳变（R 15 → SR 5）。SR 已是最高的可保养稀有度，满级后页面既无「保养」也无「更换」，任务直接收尾。

### 页面按钮分派：ROI 要覆盖整条按钮带，且别让 DirectHit 抢跑

保养结束或从入口进来时，收藏品页只有三个可能：有「更换」（R 级满级）、有「保养」（未满级）、两个都没有（SR 满级或已成珍藏品）。分派就是按这个顺序试。

两个坑都在 2026-11-11 14:58 的实机里踩到了（R 10 阶段 500/1000 时任务「成功」退出）：

- **按钮文字的位置会随页面状态左右移动**：实机测得「保养」在 x 669～781 之间、「更换」在 x 695～748 之间都出现过。原来 `ClickMaintainPage` 的 ROI 是 `720,660,90,40`、`ClickChangeButton` 是 `700,656,120,50`，只覆盖了偏右的那种状态；14:58 那次「保养」落在 `696,679`，直接漏检。现在两个 ROI 都放宽成 `620,650,220,56`，覆盖整条按钮带。
- **`ExitFlow` 是 `DirectHit`，会在同一轮把重试抢跑掉**：`next` 列表每轮按顺序各识别一次，按钮两个都漏检时 `ExitFlow` 立刻命中 → 流程判定「无事可做」→ 整个任务以成功结束。所以两个分派链都在 `ExitFlow` 前插了一个有界重读候选（`DirectHit` + `pre_delay: 1000` + `max_hit: 3`，链回分派节点），给按钮的渲染留三次机会，用完后才真的收尾。

放宽后的 ROI 也会命中面板上的「保养」（位置区间与页面那条重叠，ROI 上无法分离）。这是可接受的兜底：`ClickMaintainPage` 的自环本来就写着「面板没出现就再点一次」，指向的正是这个按钮。

### 保养后面板会被游戏自己开回来：分派前先认面板

`PageAfterMaintain` 认的是左上角「收藏品」标签，而这个标签在**三卡面板上也照样可见**（面板叠在收藏品页上）。但真正的根因更简单也更硬：

**保养结束后游戏会自己把面板开回来**，而流程在"回到页面"和"面板已出现"之间有个 0.6 秒级的窗口。2026-11-11 17:32 实机（同一次保养的连续三帧，`debug/vision/` 里 `400004127` / `400004138` / `400004141`）：

```text
17:32:52.864  画面是「等待下一步」结算态，面板还没开    → PanelVisible miss（判断正确）
17:32:54.550  画面确实是没面板的收藏品页               → PageAfterMaintain 命中（判断也正确）
17:32:55.148  点「保养」前一刻，面板已经自己开好了      → 这一下在面板上开出的是对话框 ✗
```

所以修法不是"多等一会儿"（那只是把窗口推后，而且 `max_hit` 是任务累计的、会被合法的"真回页面"消耗光），而是**在分派列表最前面加一个面板判定**：

- `CharacterPrepCollectiblePageAfterMaintain.next` 与 `SetGradeR/SR.next` 的第一候选都是 `CharacterPrepMaintainPanelVisible`；
- 该节点没有动作，命中即转 `CharacterPrepProbeEntry`（采集）→ 决策，正是"面板已开"时该做的事；面板没开时它自然 miss，继续走原来的按钮分派；
- `ClickMaintainPage.next` 里的「计划外对话框点取消」兜底保留：万一面板在"判定"和"点击"之间才开出来，它能认出来并关掉、把流程带回正轨（17:32 那次就是这样救回来的）。

同时删掉了 `CharacterPrepCollectibleWaitPanel`（原意是给面板哨兵多留几轮，但 `max_hit` 是任务累计的、会被合法回页面消耗完，实际已失效）。

### 加号与 MAX 的点击目标要收敛到中心

重复次数那一行的两个按钮，OCR 返回的框**几乎等于 ROI、比按钮本身还大**（`+` 框实测 `[713,488,32,27]`，而按钮只有 `[717,491,23,22]`），而点击点是在框内**随机取点**——所以会打空。按仓库约定"先收敛再偏移"处理：

| 节点                           | 识别框            | `target_offset` | 收敛后点击框                    |
| ------------------------------ | ----------------- | --------------- | ------------------------------- |
| `CharacterPrepClickPlusRepeat` | `[713,488,32,27]` | `[6,6,-12,-12]` | `[719,494,20,15]`（全在按钮内） |
| `CharacterPrepClickMaxRepeat`  | `[753,496,21,14]` | `[4,4,-8,-8]`   | `[757,500,13,6]`（居中）        |

负宽高保持框中心不变，只把可点区域收紧到按钮内部。

### 读不到状态时怎么办：不兜底，直接失败

有三类读数绝不能猜：**阶段**与**经验**（状态变量，用 0 兜底会当成「这阶段还没动」而多规划一整阶段）、**三档工具持有数**（用 0 兜底会把这一档判成不够用，轻则改喂更贵的档，重则三档全 0 直接走「工具箱不足」出口）。选中档读不到则可以退让：面板没有选中档时本来就不做预升级，经验条读数就是真实经验。

而**这些读数整体读不出来时，一律不做兜底**：不猜、不重试、不写「友好收尾」节点，动作直接返回失败。框架把 Custom 动作失败当成节点失败，任务随之报错结束。

理由：这类情况基本都是用户侧的问题——界面被遮挡、界面状态不对、手动干预、小字 OCR 抖动。**流程本身没问题，只是当下无法继续**，日志里写清楚就够；与其让流程去猜、去静默收尾（会掩盖真问题，例如把「读不到」当成「没有 SR 收藏品」而正常结束），不如让它停在出错的那一步，由用户判断。

```text
Decide / TierCheck / SetRepeat / ProbeGate 读不到关键读数
        → log.Error("state unreadable: flow is fine, cannot continue" + reason)
        → 动作返回 false → 节点失败 → 任务报错结束（用户手动停）
```

对应的旧机制（`retry_next` 有界重试 + `CharacterPrepCollectibleStateUnreadable` 收尾出口）已整体删除。

### 为什么「没有 SR 收藏品」必须读到明确的 0

入口判断 SR 持有数用的是 `持有数[:：]?\s*[1-9]\d*`（大于 0）。**「持有数是 0」和「这一帧没读出来」在管线里不能等价**：前者该收尾，后者该重读。所以：

- `HasSR`（持有数 > 0）→ 走 SR 流程；
- `SRCountZero`（明明白白是 `持有数 0`）→ 收尾；
- 两个都不命中 → `SelectEntered` 的 `next` 列表按 `rate_limit` 继续重试，`timeout: 8000` 之后走 `on_error` 收尾，文案说明「没有 SR 卡，或读不到持有数」。

早期版本用「卡片徽章还在不在」来判断页面有没有渲染，但持有数为 0 的卡片**照样画徽章**（实测 `frame-03-r-count0.png`），于是徽章在 + 计数漏检会被误判成「没有 SR」，还可能给用户一条「持有数为 0」的错误结论。现在这条推断已经删掉。

这里也刻意**不用 `max_hit` 做这个重试预算**：它是任务级累计计数（见 [scene-navigation.md](../../../scene-navigation.md)），选择页在一次任务里可能被进入多次，累计到上限会让后面几次合法进入直接走收尾出口。

### 入口分支：有 R 就先养 R，没有才直接用 SR

从收藏品页点展示位会进「选择收藏品」页，两张卡并排：左边 R、右边 SR，各自带「持有数」。判据是**持有数 > 0**（徽章 + 持有数正则）：

```text
有 SR（持有数 > 0）
  ├ 也有 R → 选中 R，走「R 养到 15 → 更换成 SR」这条链
  └ 没有 R → 直接选中 SR
没有 SR（持有数 = 0）→ 收尾，提示「找不到可升级的 SR 收藏品」
```

两个都没读到（既不是 > 0、也不是明确的 0）不算结论，见上文「为什么『没有 SR 收藏品』必须读到明确的 0」。

## 决策逻辑

### 目标：加权材料成本最小

保养次数本身没有额外代价（可批量、可跳过动画），所以决策的唯一目标是**少花材料**。三档工具箱的获取成本并不相等：随机宝箱的概率情报显示，高级保养工具箱开出「高级 / 中级 / 初级」的概率是 **10% / 20% / 70%**，中级箱是 **20% / 80%**。据此把三档折算成同一个「初级箱当量」：

| 档位           | 折算权重 |
| -------------- | -------- |
| 初级（R 箱）   | 1        |
| 中级（SR 箱）  | 3.5      |
| 高级（SSR 箱） | 7        |

这个比例与社区攻略里「6 : 2 : 1」的效率比是同一套东西的近似。

### 面板经验条是「预升级」显示

点页面上的「保养」进入三卡面板时，经验条显示的**不是当前经验，而是「用一次当前选中的工具组之后」的预览值**。默认选中初级箱，所以真实经验 0 会显示成 `200 / 1000`。

因此读面板时要做一次换算：

```text
真实经验 = 面板读数 − 该档位单次增量
```

「当前选中哪一档」直接读界面状态：**被选中的卡片 ITEM 横幅是蓝色、整卡带蓝框**，未选中是深色横幅。三张卡各有一个颜色匹配节点（同一个横幅 ROI，蓝色区间 `30,160,225 ~ 90,210,255`、像素数 ≥ 400），命中哪个就是选中哪一档。识别不到就按「不换算」处理：宁可少算一轮、下一轮再补，也不多做一次。

不换算的后果很直观：真实经验 0 被当成 200，剩余经验少算一次保养，规划出的次数会从 5 变成 4。

### 决策模型：在「阶段 × 经验」上做动态规划

早期版本按「每个阶段独立、取期望成本最低的档位」估算，但那样会漏掉这套系统最关键的一条规则：

> **非常成功不是「结束本阶段」，而是直接跳到下一个 5 的倍数**（0–4 → 5、5–9 → 10、10–14 → 15）。

也就是说，在 5 阶段抽中一次非常成功，会**直接跳过 6、7、8、9 四个阶段**。这条规则让「用高成功率档位去赌一次」的价值远高于它单阶段的成本对比：

- 5 阶段用高级箱：每次 70 当量、20% 概率跳到 10 阶段；3 次内命中概率 48.8%，花费 210。命中就省掉 6–9 阶段（约 500 当量）。
- 同样 3 次高级箱，若只是「按单阶段最便宜」一路用初级箱，需要约 645 当量且没有跳阶机会。

因此决策改成状态 `(阶段, 经验)` 上的动态规划：

```text
V(stage, exp) = min over (档位 t, 次数 k) of
     uses(k, p_t) × 10 × w_t         // uses 是这批实际会执行的次数，见下
   + (1 − q) × V(下一状态)           // 全部失败，经验推进
   + q × V(boundary(stage), 0)       // 命中非常成功，跳到区间边界
其中 q = 1 − (1 − p_t)^k，boundary 是下一个 5 的倍数
```

**批量成本按「期望执行次数」计，不是按对话框里设的次数。** 游戏在「次数耗尽或达到下一阶段时停止重复保养」，一旦命中非常成功就提前收工，后面没执行的次数不消耗材料，所以一批 k 次的期望消耗是 `uses(k, p) = (1 − (1 − p)^k) / p`：成功率 27.5% 时 `k=3` 的期望只有 `2.25` 次。早期版本按 `k × 10 × w` 全额计费，账面上高估了大盘批量。

不过实测这个口径**不改变任何决策**：`k=1` 时两种算法恒等（`uses(1, p) = 1`），而最优解总能由单步达成——用对照实现（把 `uses(k,p)` 换成 `k`）跑遍 R/SR 两级共 600 个状态，`V` 与选的档位、次数逐位相同。所以这条改动是把账算对，而不是改变策略；`TestSingleStepAchievesOptimum` 把这个结构性质钉住（哪天 `k=1` 不再最优，就说明模型真的变了）。

同一套模型算出来的全程期望成本：

| 策略                                          | 全程期望成本（初级箱当量） |
| --------------------------------------------- | -------------------------- |
| 每阶段独立贪心、只用初级箱（旧实现）          | 1735                       |
| 每阶段独立贪心 + 考虑跳阶、每阶段一种档位打满 | 1065                       |
| **动态规划 + 允许阶段内混合**（现实现）       | **810**                    |

规划器给出的典型动作：

| 阶段 | 起手动作                        |
| ---- | ------------------------------- |
| 0–4  | 初级箱                          |
| 5    | 高级箱 ×1（20% 直接跳 10 阶段） |
| 8    | 高级箱 ×2                       |
| 10   | 高级箱 ×2                       |
| 11   | 高级箱 ×3                       |
| 14   | 高级箱 ×1（100% 必成）          |

`decide` 报出的 `expected_cost` 就是这里的 `V(阶段, 经验)`，即「从这个状态打到满级、按最优策略继续」的期望成本。

#### 库存没有被递归进状态

递推里 `held` 只用来判断某档还剩不剩一次保养（够 10 个就参与、不够就出局），**不参与递推**，也就是说规划时把在用的档当成「后面还够用」。严格讲这是近似：某档只够两三次时，它仍会被当成后面阶段的便宜档。（本次批量实际能做几次会被当前库存夹住，见下文「库存约束」。）

之所以保留这个近似，是实测过代价的。用 4000 局/场景的蒙特卡洛（仿真语义与 DP 逐条对齐，见 `TestPlannerMatchesSimulation`、`TestBatchFlowNotWorseThanModel`）在 SR 0 → 15 的完整旅程上对比三种策略的真实初级箱消耗（这三列是一次性实验的留档：对照实现（旧的 `shouldDefer`、影子价格配给）在实验后已删除，仓库里只能复现「现实现」一列）：

| R 箱库存        | 不限量贪心（现实现） | 旧的 `shouldDefer` 让位 | 影子价格配给   |
| --------------- | -------------------- | ----------------------- | -------------- |
| 23（约 2 次）   | **837.0**            | 835.9（−0.1%）          | 835.9（−0.1%） |
| 53（约 5 次）   | **831.0**            | 833.2（+0.3%）          | 832.4（+0.2%） |
| 103（约 10 次） | **825.9**            | 838.4（+1.5%）          | 830.4（+0.5%） |
| 253（约 25 次） | **828.8**            | 826.3（−0.3%）          | 837.3（+1.0%） |
| 充足            | 820.8                | 820.8                   | 820.8          |

三种策略的差距都在 ±1.5% 以内、方向不稳定，而把库存递归进状态的状态空间是 `阶段 × 经验 × 三档剩余次数`（SR 级单 R 档就要 225 个取值），不可行。所以这里选择了最简单的写法，并把旧的 `shouldDefer` 启发式一并删掉——它在 R=103 的场景里实测反而贵 1.5%，属于「看起来更聪明、实际更贵」的复杂度。

另一条兜底是：每批保养后都会重读状态重新规划，某档真的用完后 `usable` 立刻把它排除，不会出现「规划里一直有、实际没有」的失控。

### 保养结束的落点

点「保养」之后屏幕会依次经历：对话框关闭 → **三卡面板短暂亮起（此时材料还没扣）** → 保养动画（黑屏，几秒到十几秒）→ 结算页 → 回到三卡面板。完成通知不是必然出现的。

真正的陷阱是第二步：**过渡帧和保养后的三卡面板长得一模一样**，「非常成功机率」哨兵同样命中，但经验条和持有数都还是旧值。2026-11-11 13:40 实测：点「保养」后 0.77s 面板哨兵就命中，此时仍是 10 阶段 `1000/3000`、持有 `23/715/585`；黑屏动画要到 2.5s 后才出现。若在这一帧就认定「保养完成」，流程会拿旧状态重新决策，并在动画期间反复点不到卡（本次就是连续 9 秒的空点）。

因此 `ConfirmMaintain`、`MaintainMinigame` 的 `next` **只认保养真正开跑/跑完的信号**：

| 落点       | 判据                                |
| ---------- | ----------------------------------- |
| 摩擦小游戏 | 顶部摩擦提示 或 底部「保养中…」进度 |
| 结算页     | 「点击任意处进行下一步」            |
| 完成通知   | 「收藏品保养完成」                  |

- `PanelVisible` / `PageAfterMaintain` 都不进这两个列表：前者的「非常成功机率」在过渡帧就命中，后者的「收藏品」标题在三卡面板上同样可见（实测面板命中、收藏品页命中、小游戏与结算页不命中），同样会抢跑。
- 只有 `MaintainAnimContinue`（点完结算页）和 `MaintainDone`（点完通知的确认）的 `next` 才带 `[MaintainDone, MaintainPanelVisible, PageAfterMaintain, 自环]`——这两个节点接管时保养已经落账，此时的面板才是真结果。
- 保养动画可能超出默认 20s 预算（3 次高级保养的黑屏超过 8s），两个节点都放宽到 `timeout: 60000`。

### 为什么会出现「只喂一个」

规划器有时会给出 `count=1`，这是刻意的「抽一次跳阶」策略。以 SR 级 5 阶段、经验 0 为例：

- 高级箱一次 70 当量，20% 概率直接跳到 10 阶段（跳过 6~9 四个阶段）
- 期望成本 `70 + 0.8 × V(5,1000) + 0.2 × V(10,0) ≈ 585.9`
- 对照：全程只用初级箱从 5 阶段打到满级需要 `651.0`

所以「只喂一个高级箱」是划算的赌注，命中就直接跳阶，没命中下一轮重新规划。

### 区间提示通知

在 5、10、15 阶段的区间边界上，如果在 4、9、14 阶段把重复次数拉满（MAX），会弹出「在 5、10、15 阶的区间内，无法保留超出的经验值。」的提示框，需要点「确认」才能继续。

它不是固定流程的一环，用 `[JumpBack]` 当可选步骤，**在可能弹它的两个位置都挂上**：

```text
SetRepeat       → [ [JumpBack]MaintainNotice , ConfirmMaintain ]      （点 MAX 之后）
ConfirmMaintain → [ [JumpBack]MaintainNotice , Minigame , AnimContinue , MaintainDone , self ]   （点确认之后）
```

`MaintainNotice` 自己只做一件事：**认出弹窗并点掉「确认」**，识别用 `And` 组合「确认按钮 + 提示文案」，**确认按钮放 `all_of` 首位**（点击框取 `all_of[0]`，点的是按钮不是文案）。

它**故意不写 `next`**：它是调用者列表里的 `[JumpBack]` 目标，点完确认即结束、框架自然回到调用者的列表继续（和 `CommonConfirmAction` 同一形态）。

> **坑**：最初的写法是把 `[JumpBack]CommonConfirmAction` 放进 `MaintainNotice` _自己的_ `next`。这样点掉确认后，"回到调用者"回到的是 `MaintainNotice` 自己 → 那个已经消失的按钮被反复识别 → 20 秒后节点超时 → **整个任务失败**（2026-11-11 18:03 实机：`Node.NextList.Failed name=CharacterPrepMaintainNotice` → `Tasker.Task.Failed`，而当时屏幕上其实是「非常干净」结算界面）。**`[JumpBack]` 要写在调用者的列表里**；只做一次性动作的节点不要给自己留 `next`。
>
> 另外：这个节点曾在 17:xx 被"用量普查（评估 59 次 / 命中 0 次）"判定为冗余删除，当晚就死循环了——**用量为 0 只能说明"最近没走到"，不能证明"业务上不可能"**。边界阶段（4/9/14）+ MAX 就是它的触发条件。

### 阶段内混合与批量执行

动态规划返回的是「下一步用哪一档、连续做几次」，所以同一阶段内会换档——例如 5 阶段先抽一次高级箱，没中再退回初级箱补满。

执行方式是把「连续用同一档」的若干次合并成对话框里的**重复次数**：

1. 规划器从当前状态按策略推演（假设每次都失败），统计当前档位能连续做几次；
2. 对话框默认是 1，Go 先读一次「当前/上限」：**目标正好等于上限时直接点 MAX**（一次搞定），否则算出要点几次「+」，之后**按配额逐次点击**（不再每轮读数字）；
3. 点「保养」执行。

第 2 步之所以用配额而不是每轮读数字：数字识别会落后一帧，而**到上限后「+」会变灰**——R 级每阶段只要 5 次就满（1000 经验 ÷ 200），读数为 4 时实际已经是 5，继续点就会卡在识别失败。

配额用完后也**不再回读核对**：游戏里次数文本刷新比点击慢近 1 秒，2026-11-11 13:40 实测配额用完后回读仍读到旧值 1（实际已是 2），据此补点把计划的高级箱 `×2` 点成了 `×3`，白吃一个高级工具。少点一次的后果是这轮少用一点高档料，下一轮重新规划即可，不会浪费材料。

### 摩擦小游戏

每日首次保养无法跳过，会进入「摩擦画面」小游戏：顶部提示「请摩擦画面来保养收藏品。」，底部是「保养中…」进度条，需要在人偶上左右摩擦直到进度走完。

**一次折返滑动**：`Swipe` 的 `end` 支持多段路径、`duration` 支持逐段时长，所以「右 → 左 → 右」可以写成一次不抬手的折返动作：

```jsonc
"action": {
  "type": "Swipe",
  "param": { "begin": [740, 350], "end": [[555, 350], [740, 350]], "duration": [150, 150] }
},
"repeat": 10,        // 一批 10 组折返，小游戏没完就再进本节点
"repeat_delay": 200
```

**为什么不能用「请摩擦画面」当循环条件**：一旦开始滑动，这段文案就消失，靠它判断会只滑一次就退出。持久哨兵是底部的「保养中…」+ 进度百分比（`保养中|\d+(\.\d+)?%`），它在整个小游戏期间都在，结算后消失。

节点识别因此用 `Or([顶部提示, 底部进度])` 双保险，`next` 结尾放自身：20 组做完若还在保养中就再来 20 组，做完则落到「点击任意处」或完成通知。

### 点击失效的兜底

每次点击都可能不生效（卡顿、落点偏、按钮还没响应）。**点击类动作统一用「next 里加自己」的自环兜底**：点击后目标界面没出现，就重新识别自身再点一次，不专门写重试节点。

| 动作                       | 自环判据（下一轮识别自己）                                                 |
| -------------------------- | -------------------------------------------------------------------------- |
| 点页面「保养」             | 保养面板还没出现                                                           |
| 点面板「保养」             | 保养对话框还没出现                                                         |
| 点对话框「保养」           | 对话框还在（配 `post_delay: 400`，先让对话框关掉再判断，避免连点两次保养） |
| 点「点击任意处进行下一步」 | 该提示还在                                                                 |
| 点收藏品加号               | 收藏品页还没出现                                                           |

非点击类的核对另有约定：

| 动作        | 核对方式                    | 不生效时                                                                                            |
| ----------- | --------------------------- | --------------------------------------------------------------------------------------------------- |
| 点「+」     | 配额用完后**不回读**次数    | 少点一次只是这轮少用一点高档料，下一轮重新规划；回读会把已生效的点击当成没生效，实测把 SSR×2 点成 3 |
| 点「MAX」   | 回到次数核对节点复查        | 读不到次数时只允许点一次 MAX，之后放行（MAX 生效后数字刷新比读取慢，实测会读到旧值）                |
| 「+」不存在 | 识别不到「+」时直接落到保养 | 到上限后「+」会变灰消失，若只重试「+」会一直卡到超时                                                |
| 点箱卡      | 读对话框里显示的工具箱名    | 关掉对话框回面板重选，连续 2 次不符则接受                                                           |

自环由节点自身的 `next` 超时限制次数，不会无限重试。

**计划会被非常成功打断**：游戏在「次数耗尽或达到下一阶段时停止重复保养」，一旦触发非常成功就会提前结束批量。所以每次批量回来都要重新读阶段与经验、重新规划——这也是为什么规划是「下一步动作」而不是「整段剧本」。

### 实测成本对比

用已采集的 SR 级实测概率算出的单阶段成本（单位：初级箱当量）：

| 阶段 | R 箱      | SR 箱 | SSR 箱   | 最优           |
| ---- | --------- | ----- | -------- | -------------- |
| 0    | **117.5** | 160.1 | 161.9    | R（领先 27%）  |
| 1    | **101.4** | 129.7 | 137.2    | R（领先 22%）  |
| 5    | **129.0** | 172.2 | 170.8    | R（领先 24%）  |
| 8    | **91.4**  | 107.6 | 97.3     | R（领先 6%）   |
| 10   | **138.0** | 183.6 | 180.1    | R（领先 23%）  |
| 13   | **94.8**  | 124.4 | 109.2    | R（领先 13%）  |

结论：**除 14 阶段外，全程用初级箱最省**。14 阶段的非常成功几率已经到 `10% / 45% / 100%`，高级箱一次必成、直接把剩余经验吃掉，所以反超。

### 库存约束

库存参与两件事：

1. **能不能用**：持有数 < 10（不够一次保养）的档位直接排除，于是 R 箱见底时会自动降级到 SR / SSR。每次决策都重新读三档持有数，所以某档用完后立刻出局，不会出现「规划里一直有、实际没有」。
2. **这一批最多做几次**：计划次数被 `持有数 ÷ 10` 夹住；如果规划想要 3 次而只剩 2 次，就把剩下的 2 次一次做完，而不是只喂 1 次再回来重来一遍（少一次就要多开一轮对话框）。

**但库存没有被递归进规划状态**（即规划时把在用的档当成后面还够用）。这是刻意的近似，代价已用蒙特卡洛实测过：见上文「库存没有被递归进状态」一节，三种做法（不限量贪心 / 旧的边际收益让位 / 影子价格配给）在硬库存仿真下的差距都在 ±1.5% 以内且方向不稳定，因此保留最简单的写法。旧的 `shouldDefer` 让位启发式已删除。

这也解释了为什么不做「混合凑一级」：初级箱每次 +200，正好整除 1000 与 3000，不会溢出浪费；把一阶拆成多档去凑，收益通常不足几个百分点，却要在一阶内多次开关保养对话框。

### 终止条件

- 阶段 ≥ 15 → 已满级：R 级走更换链，SR 级走统一出口收尾；
- 三档持有数都 < 10 → 日志提示「三档工具箱都不够一次保养」，走统一出口（与「没有 SR 藏品」是两个不同的出口文案）。

## 概率采集

> 本节记录**为什么采集、数据长什么样、怎么核对样本**。采集脚手架本身已移出仓库（见下面「采集脚手架已移出仓库」），运行期只剩读取侧。

### 为什么要采集

非常成功几率随「等级 × 阶段 × 档位」变化，官方不在别处公开，只能在保养面板上逐个档位点开读取。决策质量完全依赖这张表，所以做成**边跑边采集**：采集结果直接参与当次决策，不需要等全表采完。

### 补齐式采集

非常成功几率随「等级 × 阶段 × 档位」变化，官方不在别处公开，只能在保养面板上逐个档位点开读取。决策质量完全依赖这张表，所以做成**边跑边采集**：采集结果直接参与当次决策，不需要等全表采完。

每次进入三档面板，先由 Go 的 `ProbeGate` 查本地表：

```text
三档都有 → 直接进入决策
缺某一档 → 只点那一档的卡片读概率 → 写盘 → 回到门禁重新判断
```

因此同一阶段只会采一次；之后再进面板都是「查表 → 直接决策」。采集和决策都不需要人工介入。

**这行字会偶发读错**。面板上的几率是青色小字，OCR 会丢字符。2026-11-11 16:05 实证（截图 `debug/vision/*_400003469.jpg`、`*_400003474.jpg`）：

| 面板实际显示 | 记录下来的值 | 反推 OCR 读到的文本    |
| ------------ | ------------ | ---------------------- |
| `1.2%`       | `0.002`      | `0.2%`（丢了首位 `1`） |
| `5.4%`       | `0.04`       | `4%`（丢了 `5.`）      |

**为什么不加「读两遍、两次一致才落盘」的自动护栏**（实测后放弃）：

- 同一帧上重跑同一个 ROI，OCR 结果**逐字符一致**（`1.2%→1.2%`、`54%→54%`），所以「再读一次」本身不产生新信息；
- 换一个 ROI 也不行：把 ROI 收紧到只框数值行，`5.4%` 会**稳定**读成 `54%`——护栏既拦不住相关错误，又会把正确读数判成不一致而拒收（那一格会永远采不到）；
- 像素剖面显示数值行跨帧落在 y 267~290，面板自身还有几像素的上下浮动；把上边界从 270 抬到 260（留 7px 余量）是更可靠也更便宜的做法；
- 落盘时把 OCR 原始文本一起写进日志（`probe: sample saved` 的 `prob_text`），事后拿它和截图上的显示一对，就能判断这条到底对不对。

采集表按「同键不覆盖」写，所以一条误读会永久留在表里；发现后把那一格从 `prob-data.json` 里删掉，下次跑到该阶段会重采。

### 怀疑某个样本读错了怎么办：从日志找识别编号，再看那一帧截图

框架给每次识别都编了 `reco_id`，并把画面存成 `debug/vision/<时间戳>_<节点名>_<reco_id>.jpg`。所以怀疑某个采集值时：

1. 在 `install/debug/go-service.log` 里找到那条 `probe: sample saved`（或用 `debug/character-prep/collectible/prob-data.json` 定位是哪一格）；
2. 在 `debug/maafw.log`（或 `maafw.bak.*.log`）里找同一时刻的 `Node.Recognition.Succeeded` 事件，取 `__CharacterPrepCollectibleProb` 那条的 `reco_id`；
3. 用这个 `reco_id` 去 `debug/vision` 找同名截图——那一帧就是当时的画面（含选中的卡片和显示的概率），直接比对即可。

例：`SR 10` 阶段初级箱可疑 → `reco_id=400003469` → 截图显示 `1.2%`、初级卡选中 → 记录里的 `0.002` 是误读。

注意两点：截图给出的是**真值**（面板显示多少就是多少），这一步永远有效；但保存下来的那一帧不保证和 OCR 当时吃进去的帧逐像素一致（面板本身还在小幅浮动），所以**拿它离线复现那次误读未必成功**——2026-11-11 那两帧离线重跑读的都是对的。诊断靠「日志里的 `prob_text` + 截图上的显示」这对证据，而不是靠离线复现。

`debug/vision` 会越攒越多，清理后如果还需要某帧，按 `reco_id` 去回收站捞回来最省事（文件名里的 `reco_id` 是唯一的一段）。

### 决策表的落盘格式

采集表保存在 `debug/character-prep/collectible/prob-data.json`（目录不可写时退回系统临时目录，日志会打印实际路径）：

```json
{
    "SR": {
        "0": {"0": 0.036, "1": 0.11, "2": 0.25},
        "14": {"0": 0.1, "1": 0.45, "2": 1}
    }
}
```

- 第一层：稀有度；第二层：阶段；第三层：档位（`0` 初级 / `1` 中级 / `2` 高级）；值是非常成功几率（0–1，保留 4 位小数）。
- 写入幂等：同一（稀有度, 阶段, 档位）已存在就不覆盖（发现误读时删掉该格即可重采）。
- 先写同目录 `.tmp` 再改名，读侧要么看到旧内容、要么看到完整新内容，不会读到半截 JSON。
- 「读 → 改 → 写」在进程内加了锁，多个任务同时补样本不会互相覆盖。
- 仓库目录不可写时（只读检出、权限不足）自动退回系统临时目录，日志打印实际落盘的路径。
- 文件按「稀有度（R→SR）→ 阶段数值升序 → 档位」排序输出。`encoding/json` 对整数键按**字符串**排序（会把 2 排到 14 后面），所以这里是手写序列化，由单元测试守着。

### 等级靠经验条上限校正

采样的键是 `(等级, 阶段, 档位)`，其中**等级来自任务级记忆**（Pipeline 读收藏品徽章后调 `SetGradeR/SR` 记下来）。记忆一旦记错，样本就会归到错的档、决策也会用错的阶段上限与概率表。2026-11-11 00:46 实机出现过一次：等级记成 `R`、实际维护的是 SR 11 的收藏品，于是 `R-11` 被写成了 SR-11 的数值（那条落在临时目录，没污染仓库数据）。

**经验条上限是当场可验的观测**：R 级每阶段 1000、SR 级 3000。实测 56 条状态读数里「等级 ↔ 上限」零反例，所以决策与采样都以它为准，只有读不出来时才退回记忆值，并打 `grade corrected by exp cap` 告警。这一条同时挡住了两类后果：样本归错档、决策用错等级的成本模型。

### 采集与内置锚点的关系

`successProb` 先查采集表，缺失的阶段才回退到内置锚点做线性插值。锚点来自人工实测：

| 稀有度 | 阶段 | R 箱  | SR 箱 | SSR 箱 |
| ------ | ---- | ----- | ----- | ------ |
| R      | 0    | 17.6% | 55%   | 100%   |
| SR     | 0    | 3.6%  | 11%   | 25%    |
| SR     | 10   | 1.2%  | 5.4%  | 15%    |
| SR     | 11   | 2.2%  | 9.9%  | 27.5%  |

采到的阶段越多，锚点用得越少，决策越准，不需要改代码。

**采集数据的自检**（2026-11-11 复核）：

- 三级键、阶段按数值升序、每阶段三档齐全、0.1% 精度（四位小数，无二进制尾数）、幂等（同键不覆盖）；
- 与内置锚点逐值一致（R 0 阶、SR 0/10/11 阶），说明写入路径与锚点同源；
- 数值规律：同阶段三档单调 `初级 < 中级 < 高级`；每跨一次 5 的边界，三档几率一起回落、块内随阶段递增（与「区间」机制吻合）；R 级 `中级/初级 = 3.125` 在 6 个已采阶段上完全一致；SR 级块内 `高级/中级 = 2.5`（5~8 阶）与 `2.78`（10~13 阶）完全一致。
- **逐格与截图核对过一遍**（见 `debug/character-prep/collectible/probe-shots/`：`all/` 原帧、`by-sample/` 每样本一帧、两张总览图、`manifest.csv`）：
- 表里每个已有格子都能在截图上找到对应画面；
- **`SR 13 初级` 原本记成 `7%` 是误读，截图上是 `4.7%`**（帧 `…_400000158.jpg`：OCR 把 `4` 与 `7` 各框成一个框、漏掉中间的 `.`，于是只取了 `7`）→ 已按截图改成 `0.047`；
- `SR 10` 的 `0.002` / `0.04` 两条误读**从未进表**（表里是 `0.012` / `0.054`，核对无误）；
- `SR 12 初级 = 3.1%` 截图确认无误（同块比例推算的 `3.2%` 只是近似，不是硬约束）。
- 复核某个值的通用办法：从 `install/debug/go-service.log` 找到该样本 → 在 `debug/maafw.log`（含 `.bak`）里按识别事件序列找它对应的 `__CharacterPrepCollectibleProb` 的 `reco_id` → 看 `debug/vision/` 里那一帧。

## Pipeline 与 Go 的分工

| 位置                                                                        | 职责                                                                                           |
| --------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `assets/resource/pipeline/CharacterPrep/CharacterPrepCollectible.json`      | 页面／面板／对话框哨兵、箱卡与按钮识别、点击、滑动、决策路由、满级与更换分派                   |
| `assets/resource/pipeline/CharacterPrep/CharacterPrepCollectibleProbe.json` | **概率采集脚手架**（门禁、三档选卡、三个写入节点、几率读数）：与主流程文件分离，删掉即完成拆除 |
| `collectible/collectible.go`                                                | `DecideAction`（读状态 → 决策 → 改写下一步）、`SetGradeAction`（记录当前稀有度）               |
| `collectible/decide.go`                                                     | 成本模型、概率表与插值、满级／材料不足判定                                                     |
| `collectible/probe.go`                                                      | `ProbeGate`（缺哪档补哪档）、`ProbeWrite`（读概率并写盘）、排序序列化、决策快照                |
| `collectible/decide_test.go`                                                | 实测锚点成本、库存降级、材料不足、满级、插值、百分比精度、排序等回归                           |
| `collectible/simulation_test.go`                                            | 蒙特卡洛仿真一致性：DP 期望 vs 逐步仿真的平均消耗、合并批量不劣于模型                          |

识别参数（ROI、正则、颜色区间）全部留在 Pipeline，Go 通过 `ctx.RunRecognition("节点名", img)` 复用，不在代码里硬编码坐标。

**Go 侧也不写死节点名**：需要用到哪些识别节点、哪个出口节点、下一步候选列表，都由 Pipeline 通过 `custom_action_param` 传入（与洗词条的 `retry` / `next` 参数同一套做法）。参数结构：

| 字段                                                                            | 含义                                       |
| ------------------------------------------------------------------------------- | ------------------------------------------ |
| `nodes.stage_node` / `exp_node` / `prob_node`                                   | 面板状态识别节点                           |
| `nodes.repeat_node`                                                             | 对话框的「当前/上限」次数识别节点          |
| `nodes.held_nodes` / `selected_nodes` / `dialog_nodes`                          | 按档位（`R` / `SR` / `SSR`）取的识别节点   |
| `nodes.pick_nodes` / `select_nodes`                                             | 按档位取的「选中该箱」目标节点             |
| `maxed_node` / `no_material_node` / `ok_node` / `mismatch_node` / `decide_node` | 各动作的出口节点                           |
| `plus_node` / `max_node` / `next`                                               | 次数设置用的按钮节点与设置完之后的候选列表 |

参数缺失时 Go 会报错返回，不会静默路由到空节点。这样重命名或调整 Pipeline 结构时只改 `custom_action_param`，不用动 Go 代码。

## 日志与诊断

- 每次决策输出一行 `pick toolbox for next maintain`，带 `grade / stage / exp / tier / count / expected_cost / held`；
- 设置重复次数时输出 `set repeat count`，带 `current / max / target`；
- 状态读不到时不猜也不重试：输出 `state unreadable: flow is fine, cannot continue`（带 `reason` 说明是阶段／经验／哪一档持有数没读到），动作直接失败、任务报错结束；
- 面板认不出选中档时输出 `no tier card selected, treat preview exp as real exp`，按「面板不预升级」处理（这是正常状态，不是读失败）；
- 满级在读经验与持有数之前就判掉，输出 `collectible reached max stage`；
- 档位核对、次数设置的取帧失败同样按上面那条直接失败；
- 次数读不到时输出 `repeat count not recognized, keep default`，保持对话框默认的 1 次（宁可少用材料）；
- 同时把最近一次决策的输入输出写到 `debug/character-prep/collectible/last-decision.json`，用于事后核对「为什么选了这一档」；
- 每次采样输出 `probe: sample saved`，带档位、概率、**OCR 原始文本**（`prob_text`）与实际落盘路径；阶段/几率读不到时输出 `probe: read failed, skip sample`，不会把样本记到别的档位上；
- 材料不足、满级这类**业务分支**只发日志、走统一出口，不使用 StopTask；状态读不出来则直接失败（见「读不到状态时怎么办」）。

## 验证边界

这份说明里的「已实测」分三类，证据形态不同，请按类别采信。

**离线帧回放实测**（用 `maafw-live reco` 对留存的实机帧逐帧验证）：

- 三卡面板选中态的蓝色 ITEM 横幅（4 帧 × 3 档全对）、跳过保养动画勾选框的灰/蓝两态；
- 结算页文案 ROI、小游戏持久哨兵、收藏品保养对话框与完成通知；
- 「收藏品」标题在各屏幕的可见性（三卡面板命中、收藏品页命中、小游戏与结算页不命中）——正是据此把 `PageAfterMaintain` 从保养后的候选里剔除；
- **「更换」按钮的出现条件**：R 级只有 15 阶段（满级）才出现「更换」，其余等级只有「保养」；SR 满级后两个按钮都没有。因此 R→SR 只是**满级时的固定跳变（R 15 → SR 5）**，不存在按经验换算的曲线，「其它经验值下的换算」无需也无法验收；
- **按钮 ROI 的实测边界**：14:58 的失败帧（R 10 阶段）上「保养」实测在 `696,679,25,14`，13:40 / 新账号帧上在 `725,668`，`frame-11-change.png` 上「更换」在 `695,658`，13:22 帧上在 `748,671`——即 x 669～781 都出现过，放宽后的 ROI `620,650,220,56` 全部覆盖。

**单元测试覆盖**（`go test ./collectible/`，不依赖 gitignore 的采集文件：决策入口由调用方注入固定 fixture `testMeasured`，否则干净检出的 CI 会退回内置锚点而大面积失败）：

- 动态规划与实测锚点的一致性、全程成本优于单阶段贪心；
- **面板状态解析的失败分支**（`state_test.go`）：阶段／经验／任一档持有数读不到一律报错而不是拿 0 兜底，认不出选中档则按「不预升级」处理，满级在读经验之前就返回；
- **批量记账口径**（`charging_test.go`）：期望执行次数的数值与「合并批量不会比拆分更贵」的不等式，以及「最优解总能由单步达成」这一结构性质（它解释了为什么换口径不改变决策）；
- **蒙特卡洛仿真一致性**：按 DP 给出的动作逐步仿真 1500 局，平均消耗与 `expected_cost` 偏差需在 5% 以内（`TestPlannerMatchesSimulation`）；合并批量后的真实流程不得比模型更贵（`TestBatchFlowNotWorseThanModel`）；
- 库存不足降档、满级、材料不足、批量次数被库存夹住（含「计划次数大于库存时把剩余的用完」）；
- **采集落盘与报告**（`probe_test.go`）：一次运行一份报告（空文件先建、逐条追加、任务号不同即另开一份）、同一格分歧按众数合并、报告没覆盖的格子保留原值、合并表写出后可读回；决策表的首选路径不可写时退到备用路径、原子改名不留临时文件、多个候选取最新且损坏时不静默退到旧样本；
- 概率插值、百分比精度（消二进制尾数）、采集表排序与 JSON 往返、次数点击配额与档位核对重试上限。

**未覆盖的**：`DecideAction`／`TierCheckAction`／`SetRepeatAction` 的 `Run` 需要真实的 `maa.Context`，单元测试只覆盖它们调用的纯函数（状态解析、决策、落盘）与状态机，动作级的失败分支依靠 Pipeline 侧的 `retry_next`／`max_hit`／`on_error` 表达，没有自动化测试。

**实机日志与截图核对**（2026-11-11 的多轮真机运行，原始证据在 `debug/maafw.log` 与 `debug/vision/*.jpg`，`debug/` 不入库，审阅者拿不到）：
